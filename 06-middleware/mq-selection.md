# RabbitMQ vs Kafka 选型指南

---

## 一、核心定位差异

| 维度 | RabbitMQ | Kafka |
|------|----------|-------|
| 设计理念 | 传统消息队列（Broker 主动路由投递） | 分布式提交日志（append-only log） |
| 消费模式 | **Push**（Broker 推给消费者，prefetch 限流） | **Pull**（Consumer 主动拉） |
| 吞吐量 | 万级 QPS | 极高，百万级 QPS |
| 典型场景 | 业务消息、复杂路由、任务分发 | 日志、大数据管道、流处理、事件溯源 |

---

## 二、选型核心参考标准

### 2.1 吞吐量与数据规模

- 日志采集、埋点、CDC 同步、海量事件流 → 选 **Kafka**（顺序写 + 零拷贝 + 批量压缩，吞吐碾压）。
- 普通业务异步解耦、通知类消息 → **RabbitMQ** 足够，且延迟更低。

### 2.2 消息路由复杂度

- 需要 **Exchange 多种路由**（Direct / Topic / Fanout / Headers）、灵活绑定多队列 → **RabbitMQ** 强项。
- Kafka 只有 Topic + Partition（按 key hash 分区），路由能力弱，靠 Consumer Group 做逻辑订阅。

### 2.3 消息可靠性要求

两者都能做到不丢：

- **RabbitMQ**：`Publisher Confirm` + 持久化 + 手动 ACK + 仲裁队列（Raft 多副本）。
- **Kafka**：`acks=all` + ISR + `min.insync.replicas` + 手动提交 offset。

Kafka 额外提供**幂等 Producer**（PID + Sequence 去重）和**跨分区事务**，适合"恰好一次"语义要求高的流处理。

### 2.4 消费模型与回溯

- **Kafka** 消息持久化在日志中，支持**按 offset 回溯重放**（事件溯源、补数、重新计算）。
- **RabbitMQ** 消息被消费后即从队列删除，不支持回溯（除非死信/镜像保留）。

### 2.5 延迟与实时性

- **RabbitMQ** Push 模式 + 内存队列，端到端延迟更低，适合**实时业务响应**（如订单即时通知）。
- **Kafka** 为吞吐设计，单条延迟略高，但批次处理效率高。

### 2.6 运维复杂度

- **RabbitMQ** 单/少节点即可，运维简单；集群靠镜像/仲裁队列。
- **Kafka** 依赖 ZooKeeper（或 2.8+ 的 Kraft），分区、副本、ISR、再平衡（Rebalance STW 问题）调优更复杂。

### 2.7 延迟消息 / 死信

- **RabbitMQ** 原生支持死信队列 + TTL 延迟（或延迟插件），**业务延迟任务首选**。
- **Kafka** 无原生延迟队列，需外部方案（如时间轮、外部存储）。

## 三、决策树（简化版）

```
是否需要海量吞吐 / 日志流 / 事件回溯？
├─ 是 → Kafka
└─ 否 → 是否需要复杂路由 / 低延迟 / 延迟任务？
        ├─ 是 → RabbitMQ
        └─ 否 → 两者皆可，按团队熟悉度选
```

## 三、QPS 量级参考

| 中间件 | 写入吞吐 | 单条延迟 | 说明 |
|--------|---------|---------|------|
| **Kafka** | 十万 ~ 百万 msg/s | 毫秒 ~ 秒级 | 批量 + 零拷贝，攒批越高吞吐越突出 |
| **RabbitMQ** | 万级 msg/s（约 1w~5w） | 亚毫秒 ~ 毫秒级 | 单条 ACK + 持久化，实时性更好 |

> Kafka 与 RabbitMQ 的本质差异：**Kafka 用延迟换吞吐（攒批）**，**RabbitMQ 用吞吐换实时（直投）**。选型时按"要吞吐还是要延迟"权衡。

---

## 四、一句话决策

> **业务消息、复杂路由、低延迟、延迟任务** → RabbitMQ；
> **高吞吐、海量日志、流处理、事件回溯、大数据管道** → Kafka。

实际架构中两者常**并存**：用 Kafka 做数据总线/日志流，用 RabbitMQ 做核心业务的异步解耦。
