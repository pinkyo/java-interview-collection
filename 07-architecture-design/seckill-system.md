# 秒杀系统设计

> 秒杀是典型「瞬时高并发、库存有限、防超卖、防作弊」的场景。本文给出从前端到数据库的全链路设计方案，核心思想是**层层削减流量，让尽量少的请求触达数据库**。

---

## 一、需求特征与约束

| 特征 | 说明 | 设计影响 |
|------|------|---------|
| 瞬时高并发 | 活动开始瞬间流量暴涨百倍 | 多层削峰，限流 + 异步 |
| 库存有限 | 商品少，绝大多数请求必然失败 | 提前拦截，快速失败 |
| 防超卖 | 不能卖超过库存 | 原子扣减 + 唯一约束兜底 |
| 防作弊 | 黄牛/脚本刷单 | 验证码/答题/黑名单/限频 |
| 短时活动 | 通常几秒~几分钟结束 | 资源可回收，热点可隔离 |
| 一致性要求 | 不能超卖，订单最终落库 | 强一致扣库存 + 异步下单 |

**核心难点**：在极短时间内扛住海量请求，同时保证不超卖、不重复下单、系统不崩。

---

## 二、整体架构（分层削峰）

```
                    ┌──────────────────────┐
                    │        前端          │
                    │  CDN静态化/验证码/答题 │  ← 拦截 90% 无效流量
                    └──────────┬───────────┘
                               ▼
                    ┌──────────────────────┐
                    │       Nginx 网关     │
                    │  限流/黑名单/IP频控   │  ← 再拦截一批恶意/超频流量
                    └──────────┬───────────┘
                               ▼
                    ┌──────────────────────┐
                    │      应用层          │
                    │  Redis 预减库存(原子) │  ← 库存不足直接返回"售罄"
                    └──────────┬───────────┘
                               │ 有库存
                               ▼
                    ┌──────────────────────┐
                    │       Kafka MQ       │
                    │      异步排队下单     │  ← 削峰填谷
                    └──────────┬───────────┘
                               ▼
                    ┌──────────────────────┐
                    │      消费者          │
                    │  DB 扣减库存 + 创单  │  ← 真正落库，低并发
                    └──────────────────────┘
```

**削峰层次**（层层过滤，越往后流量越小）：

| 层级 | 手段 | 拦截比例（经验） |
|------|------|----------------|
| 前端 | CDN 静态化 + 验证码/答题 | ~70% |
| 网关 | 限流 + 黑名单 | ~15% |
| 应用 | Redis 预减库存，库存不足直接拒绝 | ~10% |
| MQ | 异步削峰，控制消费速率 | 剩余少量落库 |

## 三、各层设计详解

### 3.1 前端层：防作弊 + 削峰

```
1. CDN 静态化
   - 活动页静态资源（HTML/JS/CSS/图片）全部上 CDN
   - 动态部分（库存/按钮状态）用 AJAX 单独拉取
   - 效果：页面请求不打到源站

2. 验证码 / 答题
   - 点击"抢购"前需输入验证码或回答问题
   - 作用：① 拦截脚本机器人 ② 人为拉长请求时间，错开峰值

3. 按钮防抖
   - 点击后按钮置灰 5~10 秒，防止连点
   - 倒计时到点才可点击（活动未开始时按钮禁用）

4. 动态 URL
   - 下单接口 URL 在活动开始前动态下发（带加密 token）
   - 防止用户提前构造请求刷接口
```

### 3.2 网关层：限流 + 黑名单

```nginx
# Nginx 限流：令牌桶
limit_req_zone $binary_remote_addr zone=seckill:10m rate=10r/s;

server {
    location /seckill/buy {
        limit_req zone=seckill burst=5 nodelay;
        proxy_pass http://backend;
    }
}
```

```
网关职责：
├─ 限流：单 IP/单用户 QPS 限制（令牌桶）
├─ 黑名单：封禁恶意 IP/设备指纹
├─ 频控：同一用户短时间内重复请求直接拒绝
└─ 熔断：后端压力过大时返回"排队中"提示
```

### 3.3 应用层：Redis 预减库存（核心）🔥

库存不直接查 DB，而是预热到 Redis，用**原子操作**扣减，防超卖。

```java
// 活动开始前：预热库存到 Redis
redisTemplate.opsForValue().set("stock:sku:" + skuId, 100);

// 抢购时：Lua 原子扣减（判断 + 扣减 一气呵成）
String luaScript =
    "if (redis.call('get', KEYS[1]) or '0') <= '0' then " +
    "   return -1; " +                          // 库存不足
    "else " +
    "   redis.call('decr', KEYS[1]); " +
    "   return 1; " +                            // 扣减成功
    "end";

Long result = redisTemplate.execute(
    new DefaultRedisScript<>(luaScript, Long.class),
    Collections.singletonList("stock:sku:" + skuId)
);

if (result == -1) {
    return Result.fail("手慢了，已售罄");   // 绝大多数请求在此被拒
}
// 扣减成功 → 发 MQ 异步下单
kafkaTemplate.send("seckill_order", orderId + ":" + userId);
```

**为什么用 Lua**：`GET` + 判断 + `DECR` 分三步会并发超卖；Lua 脚本在 Redis 中**原子执行**，判断与扣减不可分割。

**本地标记优化**：库存扣完后在应用本地置 `soldOut=true`，后续请求直接返回售罄，连 Redis 都不查。

### 3.4 MQ 层：异步下单削峰

```
Redis 扣减成功 ──► Kafka（seckill_order）──► 消费者按固定速率落库

效果：瞬时 10w 请求 → Redis 放行 100 个（库存量）→ MQ 缓冲 → 消费者每秒落库 50 个
```

消费者控制速率（`max.poll.records`），避免 DB 瞬时压力过大。

### 3.5 数据库层：扣减库存 + 创单

```sql
-- 扣减库存（乐观锁防超卖，DB 兜底）
UPDATE sku_stock
SET stock = stock - 1
WHERE sku_id = #{skuId} AND stock > 0;

-- 创单（唯一索引防重复）
INSERT INTO seckill_order (order_id, user_id, sku_id, status)
VALUES (#{orderId}, #{userId}, #{skuId}, 'UNPAID');
-- 唯一索引 uk_user_sku (user_id, sku_id) → 重复下单报错
```

**DB 层是最后兜底**：即使 Redis 出错，DB 的 `stock > 0` 条件 + 唯一索引也能保证不超卖、不重复。

## 四、数据与缓存设计

### 4.1 Redis 数据结构

| 用途 | 结构 | Key 示例 | 说明 |
|------|------|---------|------|
| 库存计数 | String | `stock:sku:{skuId}` | Lua 原子扣减 |
| 已购去重 | Set | `bought:sku:{skuId}` | `SADD` 防重复，`SISMEMBER` 判重 |
| 本地售罄标记 | 本地变量 | — | 库存归零后应用本地缓存 |
| 限购记录 | String | `limit:user:{userId}` | 记录用户已抢次数 |

### 4.2 热点隔离

```
秒杀商品独立部署：
├─ 独立 Redis 集群（避免秒杀拖垮主缓存）
├─ 独立 DB 分库（避免扣减影响主交易）
├─ 独立应用实例（避免抢占主站资源）
└─ 独立域名/网关（流量物理隔离）
```

> 秒杀流量是"毒药"，必须与主交易隔离，否则会拖垮整个系统。

## 五、幂等与防重复

| 问题 | 方案 |
|------|------|
| 重复下单 | DB 唯一索引 `(user_id, sku_id)` + Redis Set 去重 |
| 重复扣库存 | Redis Lua 原子操作 + DB `stock > 0` 条件 |
| MQ 重复消费 | 手动提交 offset + 订单幂等（订单号唯一） |
| 超时未支付 | 延迟队列回滚库存（Redis `INCR` + DB 回补） |

## 六、兜底与降级

```
异常场景与降级策略：

1. Redis 宕机
   → 降级：直接读 DB 库存（限流加严）或返回"活动繁忙"

2. MQ 积压
   → 告警 + 动态扩容消费者；超阈值提示"订单生成中，请稍后查看"

3. DB 压力过大
   → 降级：消费速率调低 + 排队提示

4. 售罄后
   → 本地标记 soldOut=true，所有请求秒级返回"已售罄"，不再查任何存储

5. 活动异常/商品下架
   → 管理后台一键开关，熔断所有请求
```

**原则**：宁可返回"失败/排队"，也不能让系统雪崩。

## 七、整体流程串联

```
用户点击抢购
    │
    ├─ 前端：验证码/答题 → 通过
    │
    ├─ 网关：限流/黑名单 → 通过
    │
    ├─ 应用：查本地标记 soldOut？
    │       ├─ 是 → 返回"售罄"
    │       └─ 否 → Redis Lua 预减库存
    │              ├─ 失败 → 返回"售罄"
    │              └─ 成功 → 发 MQ，返回"排队中，订单生成中"
    │
    ├─ MQ：异步缓冲
    │
    └─ 消费者：DB 扣库存 + 创单
              ├─ 成功 → 发短信通知支付
              └─ 失败（DB 兜底超卖）→ Redis 回补库存
```

---

## 八、面试要点速记

1. **核心思想**：层层削峰，让尽量少的请求触达 DB。前端拦 70%，网关拦 15%，Redis 拦 10%，MQ 缓冲后落库。
2. **防超卖**：Redis Lua 原子扣减 + DB `stock > 0` 条件兜底。
3. **防重复**：DB 唯一索引 `(user_id, sku_id)` + Redis Set 去重。
4. **防作弊**：验证码/答题 + 动态 URL + 黑名单 + 频控。
5. **热点隔离**：秒杀独立 Redis/DB/应用/网关，不拖垮主站。
6. **降级兜底**：售罄标记秒回、Redis 宕机降级、MQ 积压排队提示。
7. **为什么用 MQ**：Redis 放行 N 个请求后，MQ 做缓冲，消费端控速落库，保护 DB。
