# 高可用/高并发/高性能设计

---

## 一、核心概念

| 概念 | 定义 | 衡量指标 |
|------|------|---------|
| **高并发** | 系统同时处理大量请求 | QPS / TPS |
| **高可用** | 系统长时间正常运行的能力 | 可用性（99.9% / 99.99%） |
| **高性能** | 系统快速响应请求 | RT（响应时间） |
| **高可扩展** | 系统能按需增加处理能力 | 扩展弹性 |

```
高可用性级别：
2个9（99%）     → 年停机 3.65 天
3个9（99.9%）   → 年停机 8.76 小时
4个9（99.99%）  → 年停机 52.6 分钟
5个9（99.999%） → 年停机 5.26 分钟
```

## 二、限流

### 2.1 限流算法 🔥

| 算法 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **计数器** | 固定窗口计数 | 简单 | 临界问题 |
| **滑动窗口** | 按时间片统计 | 平滑 | 内存占用稍高 |
| **漏桶** | 固定速率流出 | 流量平滑 | 突发请求被限 |
| **令牌桶** | 固定速率放令牌，请求取令牌 | 允许突发 | 实现稍复杂 |

**令牌桶原理：**

```
         ┌──────────────┐
         │  令牌生成器    │  → 每秒生成 N 个令牌
         │  (rate=N/s)   │
         └──────┬───────┘
                ▼
         ┌──────────────┐
         │    令牌桶      │  容量 = burst（最多存多少个令牌）
         │   ┌─┐┌─┐┌─┐  │
         │   │ ││ ││ │  │
         │   └─┘└─┘└─┘  │
         └──────┬───────┘
                ▼ 获取令牌
          请求到达 ─► 有令牌 → 通过
                 ─► 无令牌 → 限流
```

**追问：计数器临界问题是什么？**

```
时间窗口 0-1s：100 请求到达（正常，限流 100/s）
时间窗口 1-2s：100 请求到达（正常）
但如果在 0.5-1.5s 这 1s 内，实际处理了 200 请求！
→ 滑动窗口解决此问题
```

### 2.2 实现方案

| 方案 | 适用场景 |
|------|---------|
| Sentinel（推荐） | 分布式限流，支持流控/熔断/系统保护 |
| Guava RateLimiter | 单机限流 |
| Redis + Lua | 分布式，精确 |
| Nginx limit_req | 网关层限流 |

```java
// Guava RateLimiter（单机令牌桶）
RateLimiter limiter = RateLimiter.create(100);  // 每秒 100 个
if (limiter.tryAcquire(500, TimeUnit.MILLISECONDS)) {
    // 处理请求
} else {
    // 被限流
}
```

## 三、熔断与降级

### 3.1 熔断器状态机

```
            ┌──────────┐
            │  CLOSED  │  (正常：直接通过)
            └────┬─────┘
     失败率 > 阈值│
                 ▼
            ┌──────────┐
            │   OPEN   │  (熔断：快速失败)
            └────┬─────┘
     休眠时间到  │  (Half-Open)
                 ▼
            ┌──────────┐
            │HALF_OPEN │  (探测：放少量请求)
            └────┬─────┘
          成功    │    失败
       ┌─────────┴─────────┐
       ▼                   ▼
   ┌──────────┐       ┌──────────┐
   │  CLOSED  │       │   OPEN   │
   └──────────┘       └──────────┘
```

### 3.2 降级策略

```java
// Sentinel 降级
@SentinelResource(value = "getOrder", fallback = "fallbackHandler")
public Order getOrder(Long id) {
    // 业务逻辑
}

public Order fallbackHandler(Long id, Throwable e) {
    // 降级逻辑：返回默认值 / 缓存数据 / 提示信息
    return Order.EMPTY;
}
```

## 四、高可用设计

### 4.1 冗余设计

```
- 多机房部署（两地三中心）
- 多活架构（Active-Active）
- 同城双活 + 异地灾备
```

### 4.2 故障转移

```
服务注册发现 → 健康检查失败 → 剔除不健康节点 → 自动切换
```

### 4.3 容灾方案

| 级别 | 方案 |
|------|------|
| 应用 | 多实例 + 自动重启 |
| 数据 | 主从复制 + 备份 |
| 机房 | 多活 + 流量切换 |
| 区域 | 异地灾备 |

### 4.4 发布策略

| 策略 | 说明 | 风险 |
|------|------|------|
| **滚动发布** | 逐个替换实例 | 中 |
| **蓝绿部署** | 两套环境，流量切换 | 低（回滚快） |
| **灰度发布（金丝雀）** | 逐步放量，给一小部分用户 | 最低 |
| A/B 测试 | 不同版本对比 | 低 |

## 五、高性能优化

### 5.1 性能优化金字塔

```
                    ┌─────────┐
                    │ 业务层    │ 异步/削峰/非核心降级
                    ├─────────┤
                    │ 应用层    │ 缓存/并发/连接池/数据压缩
                    ├─────────┤
                    │ 数据库层  │ SQL/索引/分库分表
                    ├─────────┤
                    │ 架构层    │ CDN/反向代理/分布式
                    └─────────┘
```

### 5.2 缓存策略

```
浏览器缓存 → CDN → Nginx 缓存 → 本地缓存(Caffeine) → Redis → MySQL
```

### 5.3 异步化

```
同步 → 异步 → MQ 解耦

示例：用户注册
同步：验证 → 入库 → 发短信 → 发邮件 → 初始化账户 → 返回
异步：验证 → 入库 → 返回（MQ → 发短信、发邮件、初始化账户）
```

### 5.4 池化技术

- 线程池（复用线程）
- 连接池（数据库连接池 HikariCP、HTTP 连接池）
- 对象池（复用大对象）

## 面试追问集

**Q：如何设计一个秒杀系统？**

```
前端：防作弊（验证码/答题）、CDN 静态化
网关：层层限流、黑名单
业务：Redis 预减库存（原子操作）→ MQ 异步下单 → DB 扣减
数据：Redis 扛住读、热点隔离
兜底：降级方案（排队/活动结束提示）
```

**Q：如何做全链路压测？**

- 压测工具：JMeter / Locust / 自研
- 流量录制回放：流量染色标记
- 压测环境：与生产同构，或生产流量录制回放
- 数据隔离：压测数据标记（影子表/影子库）

**Q：你们的系统如何做容灾演练？**

Chaos Engineering（混沌工程），注入故障（CPU 飙高、网络延迟、节点宕机），验证系统恢复能力。工具：ChaosBlade。
