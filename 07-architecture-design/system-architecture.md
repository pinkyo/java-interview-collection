# 系统架构设计

---

## 一、架构演进之路

```
单体架构 → 水平拆分（集群） → 垂直拆分（业务线） → SOA → 微服务 → 服务网格
```

| 阶段 | 特点 | 问题 |
|------|------|------|
| **单体** | 所有功能一个 war/jar | 耦合、扩展难、发布慢 |
| **集群+分布式** | 多台部署 + 负载均衡 | Session 共享、缓存一致性 |
| **垂直拆分** | 按业务拆分系统 | 系统间接口调用混乱 |
| **SOA** | ESB 中心化治理 | ESB 成为瓶颈 |
| **微服务** | 去中心化，轻量通信 | 复杂度从代码转移到运维 |
| **服务网格** | Sidecar 代理（Istio） | 学习成本高 |

## 二、分层架构

```
┌─────────────────────────────────────┐
│         表现层（Controller）          │
├─────────────────────────────────────┤
│         业务层（Service）             │
├─────────────────────────────────────┤
│         数据层（Repository/DAO）      │
├─────────────────────────────────────┤
│         基础设施层（DB/Cache/MQ）      │
└─────────────────────────────────────┘
```

### DDD（领域驱动设计）

```
表现层 → 应用层 → 领域层 → 基础设施层

核心在领域层（Domain Layer）：
- 实体（Entity）：有唯一标识的对象
- 值对象（Value Object）：无唯一标识，属性决定相等性
- 聚合（Aggregate）：一组相关对象的集合，通过聚合根访问
- 领域服务（Domain Service）：跨聚合的业务逻辑
- 领域事件（Domain Event）：领域内发生的事件
- 仓储（Repository）：聚合的持久化接口
```

**追问：DDD 和传统三层架构的区别？**

| 对比 | 三层架构 | DDD |
|------|---------|-----|
| 核心 | 数据驱动（以表设计为起点） | 领域驱动（以业务建模为起点） |
| 业务逻辑 | Service 层代码 | 领域模型内 |
| 复杂业务 | Service 层越来越胖 | 领域模型承担 |
| 适用 | CRUD 场景 | 复杂业务场景 |

## 三、架构设计原则

### 3.1 高内聚低耦合

- **高内聚**：模块内部功能紧密相关
- **低耦合**：模块间依赖尽量少

### 3.2 分层原则

- 上层依赖下层，下层不依赖上层
- 同层之间尽量不互相依赖（通过事件解耦）

### 3.3 无状态设计

- 服务无状态，状态外置（Redis/DB）
- 方便水平扩展

### 3.4 读写分离

```
写 → 主库
读 → 从库（通过中间件路由）
```

### 3.5 冷热分离

```
热数据 → Redis/本地缓存
温数据 → MySQL
冷数据 → 归档/ES/HBase
```

## 四、常见架构模式

| 模式 | 说明 | 场景 |
|------|------|------|
| **CQRS** | 读写分离模型，命令和查询用不同数据源 | 复杂业务、高并发读写 |
| **事件溯源** | 不存当前状态，只存事件序列 | 审计、金融系统 |
| **六边形架构** | 端口-适配器，业务逻辑与外部隔离 | 可测试性要求高 |
| **整洁架构** | 依赖向内，业务实体在最内层 | 大型长期项目 |
| **BFF** | 为前端定制的后端层 | 多端（Web/iOS/Android/H5） |

## 五、技术选型

### 5.1 选型考量维度

```
功能需求：是否满足业务场景
性能：QPS、响应时间、吞吐量
可用性：故障恢复、容灾能力
可扩展性：是否容易水平扩展
运维成本：部署/监控/告警难度
社区活跃度：文档、问题解决速度
团队熟悉度：学习成本
```

| 场景 | 推荐方案 |

| Web 框架 | Spring Boot |
| ORM | MyBatis-Plus |

## 面试追问集

**Q：如何将单体应用拆分为微服务？**

1. 按业务领域拆分（订单、用户、商品…）
2. 识别边界上下文（Bounded Context）
3. 逐步拆分：先拆读再拆写，先拆边缘再拆核心
4. 数据独立：每个服务有自己的数据库
5. 通信方式：同步（HTTP/RPC）+ 异步（MQ）

**Q：你们项目的架构是什么样的？**

根据自己项目回答。标准模板：
- Nginx → Gateway → 微服务（Nacos 注册中心）→ MySQL/Redis/MQ/ES
- 监控：Prometheus + Grafana
- 日志：ELK
- 链路追踪：SkyWalking
- 部署：Docker + K8s
