# MySQL 架构与存储引擎

---

## 一、MySQL 整体架构

```
                         ┌──────────────────────┐
                         │      连接层           │
                         │ (连接管理/鉴权/线程池)   │
                         └──────────┬───────────┘
                                    │
                         ┌──────────▼───────────┐
                         │      SQL 层           │
                         │ ┌──────────────────┐ │
                         │ │ 查询缓存 (8.0 移除) │ │
                         │ ├──────────────────┤ │
                         │ │   解析器 (词法/语法)│ │
                         │ ├──────────────────┤ │
                         │ │   优化器 (执行计划) │ │
                         │ ├──────────────────┤ │
                         │ │   执行器 (调用引擎) │ │
                         │ └──────────────────┘ │
                         └──────────┬───────────┘
                                    │
                         ┌──────────▼───────────┐
                         │    存储引擎层          │
                         │ InnoDB / MyISAM / ... │
                         └──────────────────────┘
```

### SQL 执行流程

```
客户端 → 连接器（鉴权）→ 分析器（词法/语法解析）→ 优化器（索引选择/join 顺序）→ 执行器 → 存储引擎
```

## 二、存储引擎对比

| 特性 | InnoDB（默认） | MyISAM |
|------|--------------|--------|
| 事务支持 | ✅ ACID | ❌ 不支持 |
| 行级锁 | ✅ | ❌ 仅表锁 |
| 外键 | ✅ | ❌ |
| 崩溃恢复 | ✅ (Redo Log) | ❌ |
| MVCC | ✅ | ❌ |
| 全文索引 | ✅ (5.6+) | ✅ |
| 数据存储 | 聚簇索引（数据和索引一起） | 非聚簇（数据文件和索引文件分开） |
| 场景 | 在线事务处理 | 读密集型、日志类 |

## 三、InnoDB 内存结构

```
                    ┌─────────────────────────────┐
                    │       Buffer Pool            │
                    │  (数据和索引缓存，内存中)      │
                    │  ┌────────┐ ┌──────────┐    │
                    │  │ 数据页  │ │ 索引页    │    │
                    │  ├────────┤ ├──────────┤    │
                    │  │ undo页 │ │ 自适应哈希 │    │
                    │  ├────────┤ ├──────────┤    │
                    │  │ 插入缓冲│ │ 锁信息    │    │
                    │  └────────┘ └──────────┘    │
                    └─────────────────────────────┘
                                    │
                                    ▼
                    ┌─────────────────────────────┐
                    │       磁盘上的表空间文件        │
                    │  .ibd (独立表空间)              │
                    │  ibdata1 (系统表空间)            │
                    └─────────────────────────────┘
```

**追问：Buffer Pool 的 LRU 算法？**

InnoDB 使用改进的 LRU（**中点插入策略**）：
- 链表分为 young（热数据）和 old（冷数据）两个区域
- 新数据先插入 old 区域的头部
- 如果在 old 区域被再次访问，才移到 young 区域
- 避免全表扫描污染热数据

## 四、Redo Log 和 Undo Log

| 对比 | Redo Log（重做日志） | Undo Log（回滚日志） |
|------|-------------------|---------------------|
| 作用 | 崩溃恢复（crash-safe） | 事务回滚 + MVCC |
| 记录内容 | 物理日志（数据页的修改） | 逻辑日志（修改前的数据） |
| 写入时机 | 事务进行中持续写 | 事务开始前写入 |
| 配置 | 固定大小，循环写（ib_logfile0/1） | 存储于 undo 表空间 |

### WAL（Write-Ahead Logging）

先写日志，再写磁盘：
```
修改数据 → 写 Redo Log (prepare) → 写 Binlog → 写 Redo Log (commit) → 后台刷脏页
```

**追问：为什么需要两阶段提交？**

保证 Redo Log 和 Binlog 的一致性：
- 先写 Redo Log（prepare）→ 写 Binlog → 再写 Redo Log（commit）
- 崩溃恢复时：Redo Log 已 commit → 直接恢复；Redo Log 未 commit → 检查 Binlog 是否完整

---

## 五、Binlog（归档日志）

| 对比 | Redo Log | Binlog |
|------|---------|--------|
| 所属 | InnoDB 引擎层 | MySQL Server 层 |
| 用途 | 崩溃恢复 | 主从复制、数据恢复 |
| 格式 | 物理日志 | 逻辑日志（STATEMENT/ROW/MIXED） |
| 写入 | 循环写 | 追加写 |

## 面试追问集

**Q：MySQL 如何保证数据不丢失？**

1. WAL 机制：先写 Redo Log
2. 双写缓冲（Doublewrite Buffer）：防止页面部分写入（partial write）
3. Binlog 同步配置（sync_binlog=1、innodb_flush_log_at_trx_commit=1）

**Q：删除一行数据，磁盘空间会释放吗？**

不会。InnoDB 会产生空洞：
- 删除：标记删除，不回收空间
- 随机插入：页分裂产生碎片
- 解决：`OPTIMIZE TABLE` 或 `ALTER TABLE ... ENGINE=InnoDB`（重建表）
